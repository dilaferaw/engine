1. PROJECT OVERVIEW AND SCOPE
--------------------------------------------------------------------------------
A custom checkers variant with three novel mechanics: death squares, freezing,
and promotion poisoning. The engine is a pure-Python library with NO HTTP, NO
database, NO AI, and NO frontend. It will later be imported by a FastAPI
service and by a web/Android client, so its public surface must be
serializable and free of module-level mutable state.

In scope for this chunk:
  - engine/ package (constants, geometry, board, moves, legality, rules,
    notation)
  - tests/ package with unit tests and a fuzz suite
  - a REPL-playable golden game recorded as a regression test

Out of scope for this chunk: everything in §19.

2. GLOSSARY
--------------------------------------------------------------------------------
Square          An int 0..63. sq = rank*8 + file. See §3.1.
File            0..7, 'a'..'h'. file = sq % 8.
Rank            0..7, '1'..'8'. rank = sq // 8.
Player          WHITE or BLACK.
Piece kind      MAN or KING.
Home row        The four dark squares on the rank a player starts on. §3.6.
Promotion sq    a1 for WHITE, h8 for BLACK. §3.5.
Death square    A square on which any landing piece dies. §3.7, §6.
Poisoned        A side whose home row has been turned entirely into death
                because the opponent promoted. §3.8, §7.
Frozen          A piece whose only available capture is a single (length-1)
                capture, and which is therefore immobile. §8.
Single capture  A capture sequence of length 1. ILLEGAL as a move. §5.1.
Multi-capture   A capture sequence of length >= 2. The only legal captures. §5.
Grandfathered   A just-promoted king standing on its promotion square is
                safe there. §7.3.
Quiet move      A non-capture move. Includes voluntary death. §6.3, §9.5.
Legal move      A Move object returned by legal_moves(board). §9.
Playout         One full game driven by legal_moves. Used by fuzz tests.

3. BOARD GEOMETRY AND CONVENTIONS
--------------------------------------------------------------------------------

3.1 SQUARE INDEXING
  Squares are ints 0..63.
    sq = rank * 8 + file
    file = sq % 8        (0='a' ... 7='h')
    rank = sq // 8       (0='1' ... 7='8')
  a1 = 0. h8 = 63.
  a1 is a DARK square. a1-h8 is the unique 8-square dark diagonal.

3.2 ORIENTATION
  WHITE starts on ranks 6-8 (top of the printed board) and moves toward
  rank 0. White forward = rank decreasing.
  BLACK starts on ranks 1-3 (bottom) and moves toward rank 7. Black
  forward = rank increasing.

3.3 DARK SQUARES (PLAYABLE)
  A square is playable iff (file + rank) is even.
  Equivalently: file and rank have the same parity.
  There are 32 playable squares. Pieces never leave the playable squares.

3.4 DIAGONAL DIRECTIONS AND OFFSETS
  Four directions: NE, NW, SE, SW.
  Approximate offsets (valid only when you have already checked the file
  boundary — never add them blindly):
    NE = +9   (file+1, rank+1)
    NW = +7   (file-1, rank+1)
    SE = -7   (file+1, rank-1)
    SW = -9   (file-1, rank-1)
  Forward directions:
    WHITE forward = {SE, SW}   (rank decreasing)
    BLACK forward = {NE, NW}   (rank increasing)
  Man capture directions: all four.
  King move/capture directions: all four.

3.5 PROMOTION SQUARES
    promotion_square(WHITE) = a1 = 0
    promotion_square(BLACK) = h8 = 63

3.6 HOME ROWS
  The four dark squares on the rank a player starts on.
    home_row(WHITE) = {b8, d8, f8, h8} = {57, 59, 61, 63}
    home_row(BLACK) = {a1, c1, e1, g1} = {0, 2, 4, 6}

3.7 DEATH SQUARES (STATIC)
  The three static death squares on the rank a player promotes on, i.e.
  the opponent's home row minus this player's promotion square.
    death_squares(WHITE) = {c1, e1, g1} = {2, 4, 6}
    death_squares(BLACK) = {b8, d8, f8} = {57, 59, 61}
  Identity (must hold as an invariant, write a test for it):
    death_squares(p) | {promotion_square(p)} == home_row(other(p))
  The set of static death squares (regardless of owner) is the union:
    {c1, e1, g1, b8, d8, f8} = {2, 4, 6, 57, 59, 61}

3.8 POISON FLAG
  Board holds poisoned: dict[Player, bool], initially {WHITE: False,
  BLACK: False}. A side is "poisoned" when its own home_row has been
  turned into all-death because the OPPONENT promoted. See §7.

3.9 QUICK REFERENCE
    a1 = 0     b8 = 57    h8 = 63
    WHITE promo = 0,  home = {57,59,61,63}, death = {2,4,6}
    BLACK promo = 63, home = {0,2,4,6},    death = {57,59,61}
    WHITE forward ranks: decreasing.  BLACK forward ranks: increasing.
    Initial pieces per side: 12.  Playable squares: 32.

  Standard starting position (see §21 for the full map):
    WHITE: {41,43,45,47, 48,50,52,54, 57,59,61,63}
    BLACK: {0,2,4,6, 9,11,13,15, 16,18,20,22}

4. PIECES AND MOVEMENT
--------------------------------------------------------------------------------

R1.1  Board is 8x8; play on dark squares only.
R1.2  12 pieces per side, standard pool-checkers layout (3 rows x 4).
R1.3  Pieces never change square colour (guaranteed by playable squares).

R2.1  MAN moves forward one square diagonally.
R2.2  MAN captures forward AND backward. (See R3.6.)
R2.3  KING slides any distance along a diagonal (all four directions).
R2.4  KING captures by flying. (See R3.6 and §17 ambiguity A4.)
R2.5  A non-capture move cannot jump over any piece.
R2.6  A move cannot pass beyond the board edge.

Notes:
  - Quiet moves land on an empty square.
  - "Blocked" means the landing square is off-board or occupied.
  - For kings, the slide stops at the first blocker; no landing beyond it.
  - Quiet moves are only generated when no capture exists for the side
    to move (§9.5).

--------------------------------------------------------------------------------
5. CAPTURES
--------------------------------------------------------------------------------

R3.1  A single capture (length 1) is an ILLEGAL move. Only captures of
      length >= 2 ("multi-captures") are legal moves.
      Consequence: a piece whose only capture is length 1 is FROZEN (§8).
R3.2  Captures are FORCED: if any legal multi-capture exists for the side
      to move, that side must capture. Quiet moves are not available.
R3.3  MAX-CAPTURE RULE: among available captures, only the longest
      sequence(s) are legal. Length = number of pieces captured, not
      squares travelled.
R3.4  Ties for max length: the player chooses among them. The engine
      returns all tied moves; the caller chooses.
R3.5  DEATH TRUNCATION: if a capture sequence lands on a death square
      mid-way, the sequence ends there. Pieces captured BEFORE the dying
      landing still count toward length. The dying landing piece is
      removed. The resulting Move has dies = True.
R3.6  Capture directions:
        MAN:  all four diagonals (forward and backward).
        KING: all four diagonals.
R3.7  A multi-capture must not capture the same piece twice and must not
      revisit a square (see §17 ambiguity A5 for whether captured pieces
      remain as blockers during the sequence).
R3.8  A frozen piece never appears in legal_moves output (§8).

--------------------------------------------------------------------------------
6. DEATH SQUARES
--------------------------------------------------------------------------------

R4.1  Landing on a death square KILLS the piece: man or king, either
      colour.
R4.2  Death is NEUTRAL: the piece is removed; nobody gets capture credit;
      a death does not count toward capture length.
R4.3  VOLUNTARY DEATH: moving a non-frozen piece onto a death square as a
      NORMAL (non-capture) move is a legal pass. The piece is removed,
      the turn flips. See §17 ambiguity A6 (last piece).
R4.4  A frozen piece cannot voluntarily die. It cannot move at all.
R4.5  A square is a death square in the current position iff EITHER:
        (a) it is a static death square (§3.7 union), OR
        (b) it is on a home row whose owner is poisoned:
              poisoned[side] is True and sq in home_row(side)
      Note: (a) and (b) overlap on c1,e1,g1 / b8,d8,f8.
      Implementation hint: write is_death_square(sq, board) as a single
      source of truth and call it everywhere. Do not inline the logic.
R4.6  GRANDFATHERING: a just-promoted king is safe while standing on its
      promotion square. See §7.3.

Death-square status of the four squares in each home row, BEFORE poisoning:
  home_row(BLACK) = {a1, c1, e1, g1}
    a1: White's promotion square  — not a static death square
    c1, e1, g1: White's death squares — death
  home_row(WHITE) = {b8, d8, f8, h8}
    h8: Black's promotion square  — not a static death square
    b8, d8, f8: Black's death squares — death
After poisoned[BLACK] = True, ALL of {a1,c1,e1,g1} are death.
After poisoned[WHITE] = True, ALL of {b8,d8,f8,h8} are death.

--------------------------------------------------------------------------------
7. PROMOTION AND POISONING
--------------------------------------------------------------------------------

R5.1  A MAN landing on promotion_square(owner) becomes a KING.
R5.2  The promotion POISONS the side whose home row is on that rank:
      when WHITE promotes, poisoned[BLACK] = True;
      when BLACK promotes, poisoned[WHITE] = True.
      ("The opponent of the promoter is poisoned.")
R5.3  GRANDFATHERING: the promoted king is safe while standing on its
      promotion square. Once it leaves, it may never return (the square
      becomes death for everyone, including itself, from the moment of
      poisoning). See §17 ambiguity A2 for when exactly the flag flips.
R5.4  Poisoning is PER-SIDE and INDEPENDENT. Both sides can be poisoned.
R5.5  Once a side's home row is poisoned, all four squares of that row
      are PERMANENTLY death (the flag never flips back).

Implications to test:
  - After White promotes at a1: poisoned[BLACK] == True; all of
    {a1,c1,e1,g1} are death squares; White's promoted king on a1 is
    NOT removed by apply(); if it moves off a1, it cannot return.
  - After Black promotes at h8: poisoned[WHITE] == True; all of
    {b8,d8,f8,h8} are death squares; h8 grandfathering applies.

--------------------------------------------------------------------------------
8. FREEZING
--------------------------------------------------------------------------------

R6.1  A piece is FROZEN iff its only available capture is a single
      (length-1) capture — i.e. a capture that would be legal in
      traditional checkers but is illegal here.
      Formally, for one piece p:
        if captures_multi(p) is non-empty  -> NOT frozen
        elif captures_single(p) is non-empty -> FROZEN
        else -> NOT frozen
R6.2  A frozen piece is IMMOBILE: it cannot move at all, cannot
      voluntarily die. It is excluded from legal_moves.
R6.3  MUTUAL FREEZE: two opposing pieces facing each other with empty
      landing squares behind both freeze. (Classic case: each can only
      single-capture the other.)
R6.4  Freeze is computed PER TURN, BOARD-WIDE, from the current position.
      Recompute at the start of every turn. Never cache across turns.
R6.5  A frozen piece CAN be captured by a multi-capture and CAN be jumped
      over (it acts as a wall for non-capture slides).
R6.6  KINGS freeze too, at any distance (a king whose only capture is a
      length-1 flying capture is frozen).
R6.7  Freeze depends on both captures_multi and captures_single, so
      freeze_map cannot be implemented before C12 and C13/C14 are done.
      This is why freeze_map is C17, not earlier.

freeze_map(board) -> dict[int, bool]:
  For every occupied square, compute the boolean per R6.1. Return the
  dict. Legal move generation (§9) reads it.

--------------------------------------------------------------------------------
9. TURN ORDER AND LEGALITY
--------------------------------------------------------------------------------

R7.1  At the start of every turn, in this exact order:
        1. Compute freeze_map(board) for the current position (§8, R6.4).
        2. Generate all multi-captures for NON-FROZEN pieces of the side
           to move.
        3. If any captures exist: filter to max length (R3.3). Return all
           tied moves (R3.4).
        4. Else: legal moves = quiet moves of NON-FROZEN pieces,
           including voluntary death (R4.3).
R7.2  If step 3 and step 4 both yield nothing, the side has no legal
      moves; that is a draw (§10, R8.2).
R7.3  Only the side to move is considered. The opponent's frozen pieces
      are still walls (R6.5) and still capturable.

Order of legality checks is fixed. Do not reorder for "efficiency".
legal_moves(board) -> list[Move] is the single public entry point.

--------------------------------------------------------------------------------
10. WIN AND DRAW
--------------------------------------------------------------------------------

R8.1  WIN: the last player with any pieces on the board wins.
      If exactly one side has zero pieces, the other side wins.
R8.2  DRAW: legal_moves(board) == [] for the side to move.
R8.3  PRECEDENCE: check win FIRST, draw SECOND. A position with zero
      pieces for the side to move is a loss, not a draw. (Whether a
      player can voluntarily suicide their last piece is ambiguity A6;
      resolve it with a test either way.)

rules.winner(board) -> Player | None
rules.is_draw(board) -> bool

11. API-READINESS CONSTRAINTS
--------------------------------------------------------------------------------

These are hard constraints on the engine. Violating one is a scope smell
and blocks the commit.

  - No engine module imports anything from FastAPI, httpx, sqlalchemy,
    redis, pydantic, or any third-party library. stdlib + typing only.
  - No I/O in library code: no print(), no logging side-effects, no
    file writes. Use exceptions for errors, return values for state.
  - No module-level MUTABLE state. Board is the single source of truth.
    Every function that mutates takes a Board and mutates it explicitly.
  - All public functions are fully typed. mypy strict = true must pass
    for engine/. (Tests may be looser.)
  - Every public function has a docstring stating what it returns and
    citing the rule it implements, e.g. "Implements R3.5 (death
    truncation)."
  - Errors are explicit: raise ValueError with a clear message rather
    than silently returning an empty list or a sentinel.
  - Move and Board must be JSON-serializable (§13).

--------------------------------------------------------------------------------
12. DATA MODEL
--------------------------------------------------------------------------------

Player: an enum or str-like constant, values "WHITE" and "BLACK".
        Must serialize to a JSON-safe value.
Kind:   an enum or str-like constant, values "MAN" and "KING".

Piece:  dataclass. Fields: player (Player), kind (Kind). Frozen/poisoned
        are NOT on the piece — they are board state.

Board:  dataclass.
          squares:  list[Piece | None]  of length 64, indexed by square
          turn:     Player
          poisoned: dict[Player, bool]
          history:  list  (for undo; internal, not required to serialize)
        Methods (at minimum):
          setup() -> Board               classmethod, standard start
          piece_at(sq) -> Piece | None
          pieces(player) -> list[int]    (squares)
          apply(move) -> None            mutate + push history + flip turn
          undo() -> None                 pop history, reverse exactly
          to_dict() / from_dict()        §13

Move:   dataclass in notation.py.
          from_sq:   int
          to_sq:     int
          captures:  list[int]   squares of captured pieces, in capture order
          dies:      bool        True iff the final landing kills the mover
        Property:
          length -> int          == len(self.captures)
        Methods:
          to_dict() / from_dict()   §13

Freeze map: dict[int, bool] keyed by occupied square.

--------------------------------------------------------------------------------
13. SERIALIZATION SCHEMAS
--------------------------------------------------------------------------------

Move.to_dict() -> JSON-safe dict:
  {
    "from_sq":  int,
    "to_sq":    int,
    "captures": [int, ...],
    "dies":     bool
  }
Move.from_dict(d) -> Move  reconstructs exactly (roundtrip is a test).

Board.to_dict() -> JSON-safe dict:
  {
    "squares": [
      null | {"player": "WHITE"|"BLACK", "kind": "MAN"|"KING"},
      ... 64 entries, index = square ...
    ],
    "turn": "WHITE"|"BLACK",
    "poisoned": {"WHITE": bool, "BLACK": bool}
  }
Board.from_dict(d) -> Board. History may be empty on reconstruction;
equivalence is defined on squares, turn, poisoned.

Roundtrip test required: from_dict(to_dict(b)) has an identical board
per above. This is what will land in Postgres/Redis later; get it right
now.

--------------------------------------------------------------------------------
14. ERROR HANDLING POLICY
--------------------------------------------------------------------------------

  - Constructing a Move with out-of-range squares, or from_sq == to_sq,
    raises ValueError.
  - apply(move) where move is not legal for the current board raises
    ValueError with a message naming the violated rule.
    Exception: during development, you MAY temporarily skip the legality
    check to write apply() in isolation (C03-C06). By C19 the check must
    be in place. Document any temporary relaxation in a comment and
    remove it before the C19 commit.
  - undo() on an empty history raises IndexError (or ValueError; pick
    one and test it).
  - Never return [] to signal "illegal"; raise.

--------------------------------------------------------------------------------
15. TESTING PHILOSOPHY
--------------------------------------------------------------------------------

  - Tests are written by the implementer (the human), not the tutor.
  - Test names describe the RULE, not the function. Examples:
        test_man_cannot_move_backward
        test_single_capture_is_illegal
        test_max_capture_rule_filters_shorter_sequences
        test_promotion_poisons_opponent_home_row
        test_frozen_piece_excluded_from_legal_moves
        test_mutual_freeze_freezes_both_pieces
    Not: test_man_quiet_moves_2, test_legal_moves_works.
  - For EVERY rule in §4-§10, at least one positive test and one negative
    test must exist before the corresponding commit is accepted.
  - pytest, pytest-cov, hypothesis. No time.sleep. No network.
  - Fuzz tests (C23) come LAST. Fuzz without unit tests measures entropy.
  - Use fixtures and parametrize freely. Construct boards from explicit
    square sets, not from playouts, for unit tests.
