# Checkers Engine — The FastAPI / HTTP Layer

> A maintenance reference for the person who has to defend this code.

**Scope.** Everything between "a browser sends a request" and "the chess engine is asked to do something". The chess engine itself is treated as a **black box** here — we only care about its interface (what we call, what it raises). The React frontend is also a black box: we describe only what it sends and what it expects back.

A second document (`doc_engine.txt`) covers the engine and the wire protocol in more depth. A third (`doc_frontend.txt`) covers the frontend. This one is the server.

Every statement below was checked against the source in this repository. Where I am reasoning rather than quoting, it says *"inference"*.

---

## 0. The 60-second mental model

There is **one Python process**. It does three jobs:

1. Serves a JSON HTTP API — `/games/...`, `/lobby/...`
2. Serves a live event stream (SSE) — `/games/{id}/events`
3. Serves the compiled React app — everything else, from `web/dist/`

There is **no database**. Games live in a Python dict inside the process (`InMemoryGameStore`). Restart the process and every game is gone. That is a deliberate choice, not an oversight — it is what makes the demo trivially deployable.

All four game-state mutations (play, undo, rematch, leave) go through a single object called the *repository*. The HTTP layer never touches the board classes directly. That seam is what lets us swap in Postgres later without touching a route.

## 1. Vocabulary (the two acronyms you asked about)

### SPA — Single Page Application

The frontend is **not** a set of HTML pages generated by FastAPI templates. It is one HTML file (`web/dist/index.html`) plus one big JavaScript bundle. When you open the site, the browser downloads that JS once; from then on the "pages" are drawn by JavaScript in the browser and it only ever asks the server for JSON. That is why there are no routes like `/lobby.html` on the server — every unknown path falls through to the same `index.html` (see §13).

> What this means for you: FastAPI is never rendering HTML. It serves one static file, then answers JSON forever. The word "SPA" is just the name for that architecture.

### SSE — Server-Sent Events

A plain HTTP response that never ends. The client opens one request, the server holds it open, and keeps writing small text frames down the same socket:

```
data: {"board": ..., "version": 7}

: keepalive
```

Two frame types matter: `data: <json>` carries a payload, and a line starting with `:` is a comment (we use it as a heartbeat so proxies do not time the connection out).

Crucially SSE is **one-way** (server → client) and is built on ordinary HTTP, so it needs no special proxy configuration, no WebSocket upgrade, and it survives the moment you put nginx / Render / Caddy in front of it. That is why we chose it over WebSockets: nothing in this game needs the client to push.

> **Why it matters for the architecture:** with SSE, the client does not poll. The server *tells* both players when something changed. One code path, one place that touches the board, and a move made by player A appears on player B's board within milliseconds without B asking.

**Polling** (the older approach) means the client asks "anything new?" every N seconds. You can still see the fossil of it in the API: `GET /games/{id}` accepts an `?after=<version>` parameter and returns `{"changed": false}` if nothing moved. That endpoint still works and is still useful (initial load, reconnect), but the live game does not use it.

## 2. App assembly and lifecycle

### 2.1 Where the app object comes from

```python
# engine/api/__init__.py
app = create_app()
```

This line runs **at import time**. The moment uvicorn imports `engine.api`, a fully-built FastAPI app exists as a module-level global. That is why the run command is `uvicorn engine.api:app` — and why you must not import `engine.api` casually in a script (it builds an app, spins up a broadcaster, and touches the matchmaking store).

### 2.2 The factory

`create_app(repository=None, *, lobby_store=None, serve_spa=True)` in `engine/api/application.py` builds the app in a fixed order:

1. `FastAPI(title=..., version=...)`
2. CORS middleware — §3
3. Create a `Broadcaster` — the SSE fan-out, §9
4. Create the repository — `InMemoryGameStore` unless injected
5. Create the `LobbyService` — matchmaking
6. Stash all three on `app.state`
7. Mount the three routers — games, events, lobby
8. Mount the SPA at `/` — **last**, see §13

Steps 3–6 are the important part: `app.state` is a plain attribute bag that lives for the life of the process. It is how the whole app shares one repository, one broadcaster, one lobby service without any global variables and without any dependency-injection container library.

### 2.3 Why the factory exists at all

The factory is not ceremony. It is the test seam. Every API test can do:

```python
create_app(repository=FakeRepo(), serve_spa=False)
```

…and get an app with no shared state, no static files, and a repository the test controls. Without the factory you would be re-importing modules to reset state, which never works cleanly.

## 3. Middleware

Exactly one middleware is installed: `CORSMiddleware`.

```python
allow_origins = ["http://localhost:5173", "http://127.0.0.1:5173"]
allow_methods = ["*"]
allow_headers = ["*"]
```

Note what that list is: the **Vite dev server's origin**. CORS is only needed when the frontend runs on a *different* origin from the API, which is exactly the development setup (`npm run dev` on `:5173` talking to uvicorn on `:8000`).

In production the SPA is served by this same FastAPI app from the same origin, so CORS never triggers. The allowlist is therefore dev-only scaffolding that is harmless in production but would need extending if you ever hosted the frontend on a separate domain.

No gzip middleware, no request logging, no auth middleware. Anything that looks like a cross-cutting concern is handled explicitly at the point of use (errors: §6; identity: §5).

## 4. Dependency injection

The API uses FastAPI's `Depends` in its cheapest form: no classes, no `@lru_cache`, no container. Just three functions that read `app.state`.

`engine/api/deps.py` defines five aliases:

```python
TokenHeader = Annotated[str | None, Header(alias="X-Player-Token")]
NameHeader  = Annotated[str | None, Header(alias="X-Player-Name")]
Repository  = Annotated[GameRepository, Depends(get_repository)]
Lobby       = Annotated[LobbyService, Depends(get_lobby)]
Broadcaster = Annotated[Broadcaster, Depends(get_broadcaster)]
```

A handler then simply declares what it needs:

```python
def create_game(repo: Repository, token: TokenHeader = None, ...):
```

Key points worth being able to defend:

- `TokenHeader` / `NameHeader` are just typed aliases for a header. Declaring `token: TokenHeader = None` gives you the header value or `None`, with zero runtime cost and full editor support. No `request.headers.get(...)` calls scattered around.
- `get_repository` and friends are plain functions, so they are trivially overridable in tests via `app.dependency_overrides` — which is the FastAPI idiom you would reach for if a test needs a repo that raises on demand.
- The `cast(...)` calls are there because `app.state` is untyped; the protocol is what gives you static safety after that point.

This is deliberately the simplest possible DI: one indirection layer, resolved from a process-global bag, typed by a Protocol. There is no request-scoped session, because there is no database session to scope.

## 5. Routing — game endpoints

`engine/api/routes.py`, no prefix, mounted at the root.

| Method | Path | Body / query | Returns |
|---|---|---|---|
| `GET` | `/health` | — | `{"status":"ok"}` |
| `POST` | `/games` | `BoardModel?` (optional) | `201 GameCreated` |
| `GET` | `/games` | — | list of ids |
| `GET` | `/games/{id}` | `?after=<version>` | state or `{changed:false}` |
| `GET` | `/games/{id}/moves` | — | `legal_moves` only |
| `POST` | `/games/{id}/join` | — | state |
| `POST` | `/games/{id}/moves` | `MoveModel` | state |
| `POST` | `/games/{id}/undo` | — | state |
| `POST` | `/games/{id}/rematch` | — | state |
| `POST` | `/games/{id}/rematch/decline` | — | state |
| `POST` | `/games/{id}/leave` | — | state |
| `DELETE` | `/games/{id}` | — | `204` |

`engine/api/events.py`, also no prefix:

| Method | Path | Returns |
|---|---|---|
| `GET` | `/games/{id}/events` | `text/event-stream` |

### 5.1 The uniform shape of a mutating handler

Every game mutation is the same three lines:

```python
with translate():                        # exception -> HTTP status
    return repo.SOMETHING(...).state(game_id, token)
```

Read that carefully, because it is the whole design in miniature:

1. `repo.X(...)` mutates the record (and, via `_changed`, bumps the version and notifies the broadcaster — §9).
2. `.state(game_id, token)` serializes the result *from the caller's point of view*, so `your_color` is the caller's seat.
3. Returning that dict is the entire response. There is no separate "fetch the new state after the write" round trip: the write already returns it.

That is why a move feels instant to the player who made it: one request in, the new board out, no follow-up.

### 5.2 Odd ones out

- `POST /games` accepts an **optional** body. Omit it and you get a standard board (`Board.setup()`); send one and you get a custom position. That is how tests build contrived endgames over HTTP.
- `GET /games/{id}` is the polling-shaped endpoint described in §1. The `after` parameter makes it cheap when nothing changed — but note it still calls `repo.require()` first, so a missing game is a 404 either way.
- `GET /games/{id}/moves` passes `token=None` to `state()`, so `your_color` is `null` in the payload. It exists for clients that only need move legality, and it is genuinely public information (the board is already visible to anyone with the game id).
- `DELETE /games/{id}` is a maintenance endpoint with **no auth at all**. Fine for a local demo; a liability on the public internet (see §14).

## 6. Routing — lobby (matchmaking)

`engine/api/lobby_routes.py`, `APIRouter(prefix="/lobby", tags=["lobby"])`.

| Method | Path | Body | Returns |
|---|---|---|---|
| `POST` | `/lobby/heartbeat` | `?busy=` | `204` |
| `GET` | `/lobby/status` | — | `LobbyStatusModel` |
| `POST` | `/lobby/create` | — | `LobbyStatusModel` |
| `POST` | `/lobby/invites/{invite_id}/accept` | — | `LobbyStatusModel` |
| `POST` | `/lobby/invites/{invite_id}/decline` | — | `204` |
| `POST` | `/lobby/cancel` | — | `LobbyStatusModel` |
| `POST` | `/lobby/leave` | — | `204` |

These handlers look different from the game ones, and the difference is informative:

- **`_required(token)`** — the lobby cannot function without identity, so instead of threading `None` through, every lobby handler calls this helper which raises a `400` with a clear detail. That is the only place in the codebase where a missing header is an error rather than an anonymous user.
- **`_status(...)`** — the matchmaking service returns dataclasses; this helper converts them into the Pydantic response models. That is a deliberate border: the service layer never imports anything from `engine.api`.
- `heartbeat` and `decline` have no `translate()` because they cannot raise storage errors — they only touch the lobby store.

Note the shape of `LobbyStatusModel`: `state` is a plain `str` (`"idle"`, `"waiting"`, `"invited"`, `"matched"`) rather than an `Enum`. Slightly sloppy typing, but it keeps the wire format forgiving if you add a state later.

## 7. Identity — how the server knows who you are

There is no login, no session cookie, no JWT. Identity is a single header:

```
X-Player-Token: <24 hex chars>
```

The client generates it once (12 random bytes from `crypto.getRandomValues`) and keeps it in `sessionStorage` — per-tab, so two tabs are two players on one machine. That last detail is not an accident; it is what makes "play against yourself in two tabs" work and is used as the whole local test strategy.

Server side, the token is only ever compared for equality against the values stored in a game's `seats` dict (via `color_for`). Consequences worth knowing:

- The token is a **bearer credential with no expiry and no signature**. Anyone who learns it can act as that player. There is no transport security beyond the fact that you should run this behind TLS.
- `X-Player-Name` is cosmetic and separately supplied; the server truncates it and stores it per seat for display.
- Because there is no account, **a closed tab can never reclaim its seat.** The game is identified by the URL hash, but the token lives in `sessionStorage` and dies with the tab. Reopening the same game link makes you a spectator with a fresh token.

Those are design choices for a local-first game. If you ever add persistence or accounts, this is the first thing that has to change (see `AGENT.md`'s database section).

## 8. Error handling — the `translate()` pattern

`engine/api/errors.py` is 40 lines and it is the most under-appreciated file in the project.

```python
STATUS_FOR = {
    GameNotFound: 404,
    GameFull:     409,
    NotASeat:     403,
    NotYourTurn:  403,
    InviteGone:   410,
    IndexError:   409,   # undo with empty history
    KeyError:     400,
    TypeError:    400,
    ValueError:   400,   # illegal move / bad board
}

@contextmanager
def translate():
    try:
        yield
    except HTTPException:
        raise
    except Exception as exc:
        code = next((s for kind, s in STATUS_FOR.items()
                     if isinstance(exc, kind)), None)
        if code is None:
            raise
        raise HTTPException(status_code=code, detail=_detail(exc)) from exc
```

**Why this exists:** the storage and engine layers raise *domain* exceptions (`GameNotFound`, `NotYourTurn`, `ValueError("illegal move")`). They must not import FastAPI — the engine has to stay usable as a plain library. So instead of catching exceptions inside every handler, each handler wraps its body in `with translate():` and the mapping happens in one place.

Things to be able to defend here:

- **Order matters.** `HTTPException` is re-raised untouched, so a handler can still raise a deliberate `400` (as `join_game` does for a missing token) without it being swallowed.
- **Unmapped exceptions propagate**, which means they become a 500 and a traceback. That is intentional: a bug should look like a bug, not like a plausible 400.
- **`ValueError → 400` is load-bearing.** The engine signals illegal moves by raising `ValueError`. That single line is what turns "you may not do that" into a proper client error instead of a server crash.
- **`IndexError → 409`** is specifically for "undo with no moves to undo". A 409 rather than a 400 because the request was well-formed, the state just did not allow it.

One subtlety in SSE (§9): `translate()` only wraps the `repo.require()` call that happens *before* the stream starts. Once you are streaming you cannot change the status code, so mid-stream errors have to be handled by closing the connection.

## 9. The state payload — the wire contract

Every response that returns game state is produced by one method:

```python
GameRecord.state(game_id: str, token: str | None) -> dict[str, Any]
```

in `engine/storage/models.py`. It is built fresh on every call, from the perspective of the caller:

| Field | Type | Notes |
|---|---|---|
| `game_id` | `str` | |
| `version` | `int` | monotonic; bumped on every change |
| `board` | `{squares, turn, poisoned}` | 64 squares |
| `legal_moves` | `list` | `{from_sq, to_sq, captures, dies}` |
| `freeze` | `{"<square>": bool}` | only occupied squares appear |
| `winner` | `"WHITE" \| "BLACK" \| null` | |
| `is_draw` | `bool` | |
| `seats` | `{WHITE: bool, BLACK: bool}` | "is this seat taken" |
| `your_color` | `"WHITE" \| "BLACK" \| null` | **per caller** |
| `names` | `{WHITE: str\|null, BLACK: str\|null}` | |
| `history` | `list` | `{from_sq, to_sq, captures, dies, player}` |
| `move_count` | `int` | |
| `game_over` | `bool` | |
| `rematch` | `{WHITE: bool, BLACK: bool}` | |
| `rematch_declined` | `bool` | |
| `left` | `{WHITE: bool, BLACK: bool}` | |

Three things matter for the API layer specifically:

1. **`your_color` is the only per-caller field.** Two players asking for the same game at the same version get byte-identical payloads except for that one field. This is why the SSE endpoint must serialize *per subscriber* rather than broadcasting one shared payload (§9.2).
2. **`version` is the change token.** It increments on every mutation (`GameRecord.touch()`), including ones that do not change the board (join, rematch flags). The SSE endpoint uses it to decide whether it has anything new to send.
3. **`history` is a list of dicts, not engine objects.** `memory.py` appends `move.to_dict()` plus a `player` key. That is what lets the client compute "the opponent's last move" without any server help — see `doc_frontend.txt`.

**Size**, measured on this codebase: ~2.0 KB for an empty board, ~3.1 KB after 20 plies, of which history is ~69 B per move. Gzipped it is ~570 B. Sent once per move, so bandwidth is a non-issue.

## 10. Server-Sent Events — how live updates actually work

This is the most interesting part of the server and the part most worth being able to explain out loud.

### 10.1 The three objects involved

| Object | Role |
|---|---|
| `Broadcaster` (`engine/api/realtime.py`) | A dict of `game_id → list[threading.Condition]`. Knows nothing about game state. Its only job: "wake the streams watching game X". |
| `GameRecord.version` | The sequence number of the game. Any change increments it. |
| The stream (`engine/api/events.py`) | One HTTP response per open tab, holding a `Condition` and remembering the last version it sent. |

### 10.2 The chain, end to end

```
player A's tab posts a move
    -> routes.play_move -> repo.play()
        -> record.board.apply(move)          (engine does the rules)
        -> record.touch()                    (version += 1)
        -> self.on_change(game_id, version)  (wired to broadcaster.publish)
            -> Broadcaster.publish: record version, notify every waiter
    -> the HTTP response returns the new state to player A immediately

player B's open stream wakes up
    -> loop top: repo.require(game_id)       (fresh read)
    -> version != last_sent, so yield data: <full state for B's token>
    -> wait again
```

Note the asymmetry: A gets its state from the *response* to its own POST; B gets it from the stream. There is exactly one code path producing the state (`record.state`), so the two can never disagree.

### 10.3 The stream loop, line by line

```python
cond = broadcaster.subscribe(game_id)      # register a waiter
sent = -1
while True:
    record = repo.require(game_id)         # may have been deleted
    if record.version != sent:
        sent = record.version
        yield frame(record.state(game_id, token))   # per-caller state
    broadcaster.wait(game_id, cond, sent, KEEPALIVE_S)
    if broadcaster.versions(game_id) <= sent:
        yield ": keepalive\n\n"
```

Why each piece is there:

- `sent = -1` forces the first iteration to send the current state. That is how a freshly opened tab gets its initial board without a separate GET.
- The state is sent **before** waiting, not after waking. That removes a race: if a move landed between reading the record and starting to wait, the next loop iteration sees the new version anyway.
- `Broadcaster.wait` checks the published version *under the condition's lock* before blocking. Without that check there is a window where a publish happens between "read state" and "start waiting" and the wake-up is missed — the classic **lost-wakeup bug**. This is why `wait()` is 8 lines instead of 1.
- The keepalive fires only when nothing new arrived (`versions() <= sent`), so it does not interleave with real data.
- `GameNotFound` mid-stream returns from the generator, which ends the response and makes the client reconnect. Deleting a game therefore disconnects its spectators cleanly.

### 10.4 Why the payload is per-subscriber

`record.state(game_id, token)` is called *inside* each stream's own loop, with that stream's token. So two players share a socket-per-player but not a payload. If you ever "optimise" this by serializing once and broadcasting the string, `your_color` becomes whoever happened to serialize it — and every player's board flips upside down. **This is the single most dangerous simplification available in this file.**

### 10.5 Headers, and why they are not optional

```
Cache-Control: no-cache, no-transform
X-Accel-Buffering: no
```

The first stops intermediaries from caching or rewriting the stream. The second is nginx's opt-out from response buffering (`X-Accel-*` is honoured by nginx and by several cloud proxies that copied the convention). Without it a proxy will happily hold 4 KB of your frames waiting for more, and the "live" board becomes "live in 30-second batches". If you ever deploy behind a new proxy and updates feel chunky, check these two headers made it through.

## 11. Concurrency — what actually limits this server

This is the part to understand before any async refactor, because the current limit is not what it looks like.

### 11.1 Every handler is a plain `def`

None of the route handlers are `async def`. In FastAPI that means: run them in a threadpool (anyio's, default ~40 worker threads), not on the event loop. For CPU-light, in-memory work that is exactly right — it keeps the event loop free and lets blocking code stay blocking.

**The consequence:** ~40 concurrent requests is the practical ceiling, because the 41st request waits for a free thread even if the event loop is idle.

### 11.2 And now the subtle part: each SSE stream pins a thread

`StreamingResponse` with a *sync* generator iterates it via `iterate_in_threadpool`. Every call to `next(stream)` occupies a worker thread for as long as that call blocks — and our generator blocks inside `cond.wait(timeout=15)`. So while a stream is idle, **one worker thread is parked doing nothing**, for as long as the tab is open.

That gives the real capacity model:

> **max simultaneously open game tabs ≈ number of threadpool workers (~40)**

…and games in progress compete with those threads for every POST. So roughly:

| Load | Behaviour |
|---|---|
| a handful of games | completely fine, no measurable latency |
| ~30 open tabs | starting to queue |
| 40+ open tabs | streams starve each other **and** ordinary requests start waiting |

You can raise the threadpool (anyio's `to_thread` limiter), but that is just buying time with memory. The structural fix is to make the SSE generator `async def` and replace `threading.Condition` with `asyncio.Event` / an `asyncio.Queue` per subscriber — then an idle stream costs a coroutine (a few KB) instead of a thread (8 MB of stack). That is the async refactor, and it is confined to `events.py` + `realtime.py` + changing those two handlers to `async def`. **Nothing in the engine needs to change.**

### 11.3 What is NOT a bottleneck

- **Bytes:** ~3 KB per move, gzipped ~570 B.
- **CPU:** the engine is trivial; a move is microseconds.
- **The repository:** a dict lookup.

The only real constraint is open streams vs threads. Worth saying out loud in any interview answer about this project.

## 12. The repository seam — what a new backend must implement

`engine/storage/base.py` defines a `Protocol` (structural typing — no inheritance needed):

```python
ids() -> list[str]
require(game_id) -> GameRecord                 raises GameNotFound
create(board, token, name) -> (id, GameRecord)
join(game_id, token, name) -> GameRecord        raises GameFull
play(game_id, token, move) -> GameRecord        raises NotYourTurn, ValueError
undo(game_id) -> GameRecord                     raises IndexError
request_rematch(game_id, token) -> GameRecord   raises NotASeat
decline_rematch(game_id, token) -> GameRecord
leave(game_id, token) -> GameRecord
delete(game_id) -> None                         raises GameNotFound
```

That is the whole storage contract: nine methods. Everything the HTTP layer can do to a game goes through them.

Rules of the seam, and why they are easy to break:

1. **Every mutation must call `_changed`.** In `InMemoryGameStore` that is a helper that does `record.touch()` (version += 1) and then `on_change(game_id, version)` (wake the broadcaster). A new backend that forgets the second half will accept moves but every open tab will sit frozen — **the single worst bug you can introduce here.** `AGENT_NOTE.md` records this as a past trap.
2. **`state()` lives on the record, not the store.** So a SQL backend still needs a `GameRecord`-shaped object with a real `Board` in it; the store hydrates it on read. The API does not care where it came from.
3. **Token → colour mapping is `color_for(seats, token)`**, a plain function. Keep it. Do not reinvent it per backend.
4. **Routes must never import a concrete store.** Only the `Repository` alias. The one place a concrete store is named is `create_app`.

`AGENT.md` has a longer discussion of the sync-vs-async storage question; the short version is that staying synchronous (sync driver, `def` handlers, threadpool) is the low-churn choice and the threadpool model already accommodates it. Going async in storage would force every handler and the SSE generator to be async at the same time, which is the bigger refactor.

## 13. Static files — how the React app gets served

```python
dist = <repo>/web/dist
if serve_spa and dist.is_dir():
    app.mount("/", StaticFiles(directory=dist, html=True), name="web")
```

Four things to understand:

1. **It is mounted LAST.** A `mount` at `/` swallows every path that no router claimed. Mounting it before the routers would make `/games` a 404 from the static handler. Order in `create_app` is load-bearing.
2. **It reads from disk per request.** No caching layer. So `npm run build` takes effect on the next request with **no server restart** — which is why a stale frontend bug looks like a backend bug (this bit us once).
3. **`html=True` gives SPA routing.** Unknown paths fall back to `index.html`, so the client's hash-based routing (`#/game/<id>`) works. Note this is client-side routing; the server never sees the hash.
4. **`serve_spa=False` in tests** means API tests never depend on a build artefact existing. If `web/dist` is missing, the app still starts and the API still works — you just get 404s for the UI.

Because of this mount, "frontend" and "backend" are **one deployment**. That is why there is no separate Vite server in production, and it is the thing you asked about: the React app is a *file* the FastAPI app hands out once, after which the browser talks to the JSON API.

## 14. Observations, risks, and things to be ready to answer

These are the honest weak points. Better to know them than to be surprised.

### 14.1 Authorization gaps (demo-grade, not production)

- `POST /games/{id}/undo` takes **no token** and undoes the last move for anyone who asks. It is a shared "takeback" button, not a per-player one.
- `DELETE /games/{id}` is similarly unauthenticated.
- `InMemoryGameStore.play` accepts a move from an **unseated token** (a spectator), because it only rejects when `color is not None and color != turn`. Documented in `AGENT.md`.
- Any holder of a game id can read its full state (`GET /games/{id}`), and the id is in the invite URL. Acceptable for a friendly game, not for a ranked one.

> If asked "is this secure?" the honest answer is: **it has identity, not authorization.** Tokens identify a seat for gameplay purposes; they do not guard destructive endpoints.

### 14.2 Single-process assumptions

- `InMemoryGameStore`: games are per-process. Run `--workers 4` and matchmaking (Redis-backed) pairs two players into a game that only one worker can see. **Pin `--workers 1`.**
- `Broadcaster`: in-process conditions. Multi-worker needs Redis pub/sub; the contract is documented at the top of `realtime.py` and there is a Redis precedent in `engine/matchmaking/redis_store.py`.
- Cold start or redeploy wipes every game. By design.

### 14.3 Loose ends worth fixing cheaply

- `pyproject.toml` still lists `testpaths = ["tests", "deeps_tests"]` but `deeps_tests/` was deleted. Pytest tolerates a missing path (verified: exit 0, 119 tests), so it is cosmetic drift — but it makes the config look stale.
- The health endpoint is `/health` (not `/healthz`). Any platform health check must be configured to that path explicitly.
- `LobbyStatusModel.state` is `str`, not an enum: typos in the service would not be caught by the schema.
- `GET /games` returns every game id, unbounded. Fine locally; a leak in public.

### 14.4 Things a reviewer might ask, with answers

**"Why SSE instead of WebSockets?"**
Updates are one-directional (server → client); moves go over normal POSTs. SSE is plain HTTP, needs no upgrade handshake, survives every proxy, and reconnects with a built-in retry story. A WebSocket would add a second transport, a second auth path and a second failure mode for no gain.

**"Why not just poll?"**
Polling was the original design and its remains are visible (`?after=`). It costs a request per client per interval forever, and latency is bounded by the interval. SSE pushes exactly when something changes and costs one idle socket.

**"What happens if a client misses a frame?"**
Nothing is missed, because every frame is the *complete* state, not a delta. A dropped frame self-heals on the next one, and a reconnect immediately gets a full snapshot (the `sent = -1` initial send). That is the argument for sending full state instead of deltas: correctness is trivial, and the payload is 3 KB.

**"What happens if the network dies silently?"**
Historically, nothing — the fetch stayed pending forever and the board froze until reload. That is why the client now runs a watchdog (silence > 32 s → abort and reconnect) and counts any bytes, including keepalive comments, as liveness. The server side was always fine; the client was blind to silence.

**"Can two players receive different bytes for the same game?"**
Yes, by design: `your_color` differs. Everything else is identical because it comes from the same `state()` call on the same record.
